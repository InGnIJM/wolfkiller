# 角色行动契约与规则一致性设计

## 目标

修复角色提示词与游戏引擎之间的规则漂移，并将角色行动改为可扩展、可校验的结构化契约。此次范围仅覆盖提示词和规则执行；鉴权、回放脱敏、事件跨局隔离等问题留待后续处理。

## 已确认规则

- 女巫每晚只能使用一瓶药；解药、毒药各整局一次。
- 狼人可以攻击任意存活玩家，包括自己和狼队友。
- 除狼人知道狼队友外，玩家仅依据公开信息和自身私有信息行动。
- Prompt 不向角色展示依据身份筛选的目标白名单，也不预示策略性目标。
- 服务端只校验客观合法性：阶段、能力剩余、目标存在和目标存活。
- 首次平票后全体存活玩家补充发言并复投；复投仍平票才无人出局。
- 非法模型输出只允许一次纠错重试；仍失败则安全放弃，不随机代选。

## 方案

采用“单一规则源 + 上下文行动契约”。角色负责决策，规则代码负责解释和执行；Prompt 从同一契约读取当前局面的事实，而不复制独立的静态规则版本。

```text
角色可见状态 + 当前任务
  -> 严格函数调用或 JSON 降级输出
  -> ActionCommand
  -> 角色/阶段行动契约
  -> GameEngine 执行、记录和推进阶段
```

### 行动契约

每个行动使用统一的 `ActionCommand` 形状：

- `action_type`：当前上下文允许的动作枚举；
- `target_seat`：目标座位，不能行动时为 `null`；
- `reasoning`：受长度限制的简短决策依据。

夜间行动和投票不再依赖“Prompt 中要求输出 JSON”的软约束。角色/阶段契约声明动作名称、目标是否必需、客观验证规则和安全降级方式。新增角色需要注册自己的行动契约并接入相应阶段，不应修改既有角色的目标规则。

契约验证不将目标候选集回显给模型。它仅在模型提交后检查目标是否存在、是否存活，以及能力和阶段是否匹配。狼人行动不附加阵营限制，因此自刀和刀队友保持合法。

### `RoleSpec` 注册与调度

规则源由可注册的 `RoleSpec` 和 `ActionContract` 组成，而不是按“女巫/预言家”等名称在引擎中分支：

- `RoleSpec` 至少声明 `role_id`、可行动阶段、私有信息构建器、行动契约和结算处理器；
- `ActionContract` 至少声明触发阶段、动作枚举、执行者选择器、目标语义、单局/单夜次数限制、结算优先级、语义校验器及安全降级动作；
- 引擎按当前阶段、结算优先级和存活执行者查询注册表并调度。新增角色只注册自己的规范与处理器，不修改已有角色分支或其目标限制；
- 角色、行动和次数的实例状态以 `game_id`、`round_id`、`actor_seat`、`contract_id` 为键持久化；同一行动键至多接受一次，防止重试或重复事件造成二次结算。

这一定义只提供角色可执行的动作类型和客观校验，不提供“按阵营/身份应选哪些座位”的策略候选名单。

### 动态 `GameConfig` 与角色实例

`GameConfig` 以 `role_counts: Mapping[role_id, int]` 作为角色组成的唯一来源，不再以固定的女巫、预言家、狼人等字段表达板子。创建游戏前必须校验：每个 `role_id` 都已注册、数量为非负整数、所有数量之和等于 `player_count`，并满足该 `RoleSpec` 声明的配置约束。

游戏创建器按通过校验的 `role_counts` 生成角色实例并分配到座位；每位玩家恰有一个实例角色。引擎、Prompt 和公开板子说明均从同一份配置和实例状态读取信息。新增角色因此只需注册 `RoleSpec` 并在配置提供相应计数；未知角色、计数不匹配或未分配完整座位的配置必须在开局前拒绝。

### 唯一行动校验入口

模型输出不得声明行动者、阶段、轮次或资源状态；引擎从当前任务注入 `actor_seat`、`phase`、`round_id` 和 `contract_id`，再将它与 `ActionCommand` 交给唯一入口 `validate_and_accept(command, state)`。校验和接受顺序固定为：

1. 解析结构和字段类型；
2. 当前阶段、行动归属和同一行动是否已接受；
3. 次数限制与资源剩余；
4. 目标必填性、座位存在性和存活性；
5. 动作专属的客观语义；
6. 原子地预留资源、记录已接受命令，再进入结算。

`pass`/`abstain` 必须使用 `target_seat=null`；要求目标的动作不得使用 `null`。女巫 `save` 的目标必须等于该局当夜已记录的刀口，`poison` 仅在毒药未使用且目标存活时有效。这里的“等于刀口”是对已提交命令的服务端事实校验，不向模型生成目标白名单。

### 女巫

将当前分离的救人、毒人决策合并为每夜一次 `witch_action`。该动作只能为 `save`、`poison` 或 `pass`：

- `save` 仅在存在当夜刀口且解药未使用时生效；
- `poison` 仅在毒药未使用时生效，目标必须为存活玩家；
- 一次 `witch_action` 后，当夜不再请求第二个女巫动作；
- 引擎和结算层均验证药品消耗，避免 Prompt 或解析器绕过规则；
- 刀口仅按已确认的女巫私有信息规则注入 Prompt。

### 平票

投票状态持久化 `vote_round`、`is_tiebreak`、候选、已补充发言座位和已投票座位。`abstain` 是合法投票：它计入“已投票”，但不计入任何座位票数。

首次出现至少两名最高票候选人的平票后，引擎将 `is_tiebreak=true`，按固定顺序让全部存活玩家补充发言，再开启复投；复投仍平票，才记录无人出局并进入夜晚。全体弃权或没有任何最高票候选人不构成平票，直接无人出局。Prompt 从状态读取当前轮次和流程，不再描述“首次平票立即无人出局”。

### 动态 Prompt

系统 Prompt 改为紧凑的通用规则，删除固定的九人角色数量。每次任务 Prompt 由 `GameConfig` 生成公开板子配置、当前阶段、公开存活/死亡座位和当前角色私有信息。

历史对话和已记录决策依据保持为游戏数据，而不是可执行指令；它们必须有明确边界标识。详细 `thinking` 不再强制生成和长期回灌，改为长度受限的 `reasoning`。

Prompt 的可见性和行为约束必须可测试：非狼人不得获得其他玩家的身份或由身份推导的目标集合；历史内容以明确的“不可执行游戏记录”数据边界包裹，不能覆盖系统规则；行动任务只说明动作契约和客观输出形状，不暗示应选择某一阵营或座位。

### 结构化输出与降级

默认通过 DeepSeek strict Function Calling 输出行动。工具 Schema 固定字段、类型、枚举和 `additionalProperties: false`。strict 模式不可用时，降级到 JSON Output 并用 Pydantic 严格解析。

每个 `ActionContract` 生成对应的函数/JSON Schema；两条传输路径共享同一个 Pydantic 解析器和 `validate_and_accept` 入口。状态机为：`STRICT_CALL -> PARSE_AND_VALIDATE -> ACCEPT`；仅在 strict 的能力配置、Schema 不被供应商支持或供应商明确拒绝 strict 请求时切换为 `JSON_CALL`。网络、限流或模型正常响应但内容非法不视为 strict 不可用。

`STRICT_CALL` 或 `JSON_CALL` 的格式、Schema 或语义失败均进入一次 `CORRECTIVE_RETRY`，纠错请求必须复用当前传输路径和原行动键；再次失败进入 `SAFE_FALLBACK`：夜间行动为 `pass`，投票为 `abstain`。每次转换记录失败分类、`game_id`、`round_id` 和行动键用于度量，绝不随机选择目标；能力降级本身不额外消耗这一次模型输出纠错机会。

## 修改边界

预计修改：`prompt_builder.py`、`llm_client.py`、`output_parser.py`、`game_engine.py`、`action_resolver.py`、`roles/witch.py`、相关模型及测试。实际实现按现有模块边界拆分，避免把角色策略、传输格式和规则执行混在一个文件中。

## 验收标准

- 女巫无法同夜双药，且每种药只能使用一次。
- 狼人自刀、刀狼队友均可执行；死亡或不存在的目标被拒绝。
- 非法输出最多重试一次，之后安全放弃；预言家不再随机查验兜底。
- 首次平票触发补充发言和复投，复投平票才无人出局。
- `vote_round`、补充发言和投票状态在重试/重连后保持一致；全弃权直接无人出局，不错误进入复投。
- 非九人或新增角色配置生成正确的公开板子说明与行动任务。
- 新角色可以仅注册 `RoleSpec`/`ActionContract` 接入调度，不修改既有角色的目标限制或引擎角色分支。
- 对每种契约覆盖动作归属、目标必填性、资源耗尽、重复提交、动作专属语义和安全降级；女巫 `save` 必须指向当夜刀口。
- 以 mock 覆盖 strict 成功、strict 能力降级、JSON 成功、一次纠错成功和安全放弃；不依赖真实 LLM 或真实 API Key。
- 对 Prompt 覆盖不同人数/角色、玩家可见信息、历史数据边界和无身份策略白名单。测试统计约定在实施计划中按实际模块写明 `pytest --cov` 目标并达到 100% 路径覆盖。

## 不在本轮范围

- REST/WebSocket 鉴权与观众信息脱敏。
- 多局 EventBus 的 `game_id` 隔离。
- 前端构建、回放和无障碍问题。
- 生产部署、限流和成本治理。
