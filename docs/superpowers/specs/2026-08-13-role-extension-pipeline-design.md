# 角色扩展流水线设计

## 1. 背景与目标

当前项目已经建立了 `RoleSpec`、`ActionContract`、`ActionCommand`、`RoleRegistry` 和统一的模型输出解析入口，也已经把角色数量改为动态 `role_counts`。这些改动解决了角色注册、结构化输出和基础行动调度问题，但源码仍有以下扩展瓶颈：

- `ActionValidator` 直接读取并修改 `GameState`，且按 `save`、`poison` 等动作名包含角色专属分支；
- `ActionResolver` 直接修改玩家生死、药品、查验结果，并固定知道狼人、女巫、预言家和猎人的结算顺序；
- `GameEngine` 仍按具体角色查找行动者、准备角色资源、打开猎人响应和推进若干专属步骤；
- `StateFilter` 与 `PromptBuilder` 仍按角色名拼装女巫、猎人等私有信息；
- 当前 `RoleSpec` 只声明工厂和契约，没有承载适用条件、纯校验、结算和响应窗口行为。

因此，“注册了角色”还不等于“角色机制可独立扩展”。本设计的目标是引入受约束的角色 Hook 流水线：新角色在角色规范模块中声明何时行动、能看见什么、如何校验以及产生哪些效果；通用引擎只负责编排，不再认识角色名或动作名。

完成后，新增一个能由既有通用效果表达的角色，只需新增角色规范模块并加入注册/配置，不得修改 `game_engine.py`、`action_validator.py`、`action_resolver.py`、`prompt_builder.py` 或 `state_filter.py`。

### 1.1 明确非目标

- 本设计不允许角色 Hook 获得或直接修改 `GameState`、玩家对象、角色对象或数据库会话；
- 不支持从网络热加载不受信任的第三方 Python 代码；角色代码与服务端代码一同发布和审计；
- 不在本轮新增正式玩法角色、前端角色界面或运营配置后台；守卫仅作为扩展验收样例；
- 不重写 REST、WebSocket 观战协议，也不改变已经确定的公开事件脱敏边界；
- 不承诺任何未知机制都能零核心改动。若机制需要全新的状态变更原语，必须先独立扩展并版本化 `GameEffect` 代数和 `EffectApplier`，之后角色才能使用它；
- 不在本轮引入跨进程分布式调度或动态脚本沙箱。

## 2. 方案选择

### 2.1 推荐：纯 Hook + 类型化 Effect

`RoleSpec` 注册无状态纯函数 Hook。Hook 只接收不可变的 `ActionContext` 和 `ActionCommand`，返回零个或多个 `GameEffect`；唯一的 `EffectApplier` 校验并原子写入游戏状态。调度、输出解析、幂等、重试、隐私投影和事件派发仍由核心流水线统一负责。

该方案允许守卫、丘比特式关系、死亡响应等角色表达独特逻辑，同时不会把状态写权限或其他玩家的隐藏身份交给角色代码。它也使每个角色机制可以用纯输入/输出测试覆盖。

### 2.2 不选：纯数据规则 DSL

纯配置适合“选择目标、消耗资源、造成伤害”这类组合，但遇到连锁死亡、条件响应、关系建立和多行动聚合时会迅速演化成一门难以调试的规则语言。继续扩大 DSL 会重复实现分支、类型系统、错误栈和调试工具，复杂度高于受约束的 Python Hook，且无法自然复用现有测试能力。

### 2.3 不选：角色插件直接操作 `GameState`

让独立插件模块获得完整状态最灵活，但会绕过资源次数、幂等、隐私和事件审计。任一 Hook 都可能读取未知身份、部分写入后抛错或重复结算，核心规则无法再提供可信保证。因此插件模块可以作为代码组织方式，但不能拥有状态对象；它仍必须遵守本设计的 Context/Effect 边界。

## 3. 核心不可变类型

所有核心类型都必须是深度不可变值：Python 层使用 `frozen=True`，序列使用 `tuple`/`frozenset`，映射在构造时复制为只读映射；不得在字段内藏入可变对象或状态引用。类型必须可序列化、可生成稳定摘要并具有明确的 `schema_version`。

### 3.1 `RoleSpec`

`RoleSpec` 是一个角色的唯一规则入口，至少包含：

- `role_id`、`display_name`、`camp_id`、`schema_version`；
- 初始角色资源和角色私有数据的声明式 Schema；
- `contracts: tuple[ActionContract, ...]`；
- 角色组合约束，例如最少/最多数量、依赖或互斥标签；
- 私有可见性声明：角色本人、阵营队友、关系成员可读取哪些命名空间；
- 静态的角色说明和 Prompt 片段，不包含局面策略或目标白名单；
- Hook 集合：适用条件、语义校验、行动结算和事件响应。Hook 必须是无状态函数引用，不能闭包捕获可变状态、客户端或存储连接；
- 允许产生的 `GameEffect.kind` 集合，用于最小权限校验。

角色工厂只负责模型决策代理等非规则运行时对象的装配；游戏规则和角色资源定义必须来自 `RoleSpec`，不能藏在角色子类构造函数中。

### 3.2 `ActionContract`

`ActionContract` 是一次行动的完整客观契约，至少包含：

- 全局唯一的 `contract_id` 和版本；
- `schedule_point`、`order`、行动者资格和可选的响应事件条件；
- 允许的 `action_types`、是否需要目标、目标的客观形状约束；
- 单窗口、单轮、单局次数限制及所需资源；
- 聚合方式，例如逐人结算、收齐后多数决或按座位稳定排序；
- strict JSON Schema 和 `fallback_action_type`；
- Hook 引用与允许产生的效果集合。

契约只描述客观合法性，不返回“应该选择哪些座位”的策略白名单。狼人契约的目标约束是“存在且存活”，不会按阵营排除自己或狼队友。

### 3.3 `ActionContext`

`ActionContext` 是某一行动或响应窗口的最小只读快照，包含：

- `game_id`、状态修订号、配置版本、轮次、阶段、`window_id` 和调度点；
- 引擎绑定的行动者座位、角色 ID、存活状态和角色资源只读快照；
- 当前行动者可见的公开状态、私有事实和关系数据；
- 当前契约允许读取的已接受命令摘要或聚合结果；
- 若为响应窗口，则包含经过可见性裁剪的触发事件、原因和 `source_event_id`；
- 当前行动键以及次数计数快照。

`ActionContext` 明确不得包含 `GameState`、完整玩家表的隐藏字段、其他角色对象、可写容器、日志器回调或数据库句柄。Context 由通用投影器按可见性标签生成；Hook 不能自行向状态查询更多信息。

### 3.4 `ActionCommand`

`ActionCommand` 保持模型可提交的最小形状：`action_type`、`target_seat`、受长度限制的 `reasoning`。模型不得填写行动者、角色、轮次、阶段、窗口、资源、可见性或幂等键；这些字段由引擎从已签发请求绑定。模型配置必须冻结对象并拒绝额外字段。

### 3.5 `GameEffect`

`GameEffect` 是 Hook 能产生的唯一状态变更意图，至少包含：

- `effect_id`、`schema_version`、`kind`、`source_action_key`；
- 目标引用、类型化负载和公开/私有可见性标签；
- `expected_revision` 及必要的前置条件；
- 因果链 `source_event_id` 和稳定的排序键。

初始效果代数提供通用原语：接受行动、消耗/设置角色资源、设置角色私有数据、添加/移除临时状态、添加/移除关系、记录私有事实、提交伤害或保护、标记死亡、发出领域事件。角色不得自定义任意回调型 Effect，也不得通过负载携带对象引用。

`EffectApplier` 是唯一写入口。它先验证整个 Effect 批次的 Schema、来源权限、修订号、前置条件和内部冲突，再在一个事务中全部应用；任一 Effect 失败时整批不写入。Validator、Resolver、Hook、Prompt 和投影器均无写权限。

## 4. Hook 契约与权限

角色规范可以注册以下纯 Hook：

- `is_applicable(context) -> bool`：判断该已投影行动者在当前窗口是否获得请求；
- `validate(context, command) -> tuple[RuleViolation, ...]`：补充契约无法声明的客观语义检查；
- `resolve(context, command) -> tuple[GameEffect, ...]`：将已验证命令解释为效果；
- `react(context) -> tuple[GameEffect, ...]`：处理无需模型决策的确定性事件响应；需要玩家决策的响应仍签发普通 `ActionRequest`；
- `aggregate(context, commands) -> tuple[GameEffect, ...]`：在收齐同一契约的命令后做多数决等确定性聚合。

所有 Hook 必须满足：同一输入产生字节级等价输出；不访问时间、随机数、文件、网络、环境变量和全局可变状态；不调用模型；不写日志中的私密原文；在固定时间预算内返回。需要随机性时，引擎把已记录的随机结果作为 Context 事实注入，而不是让 Hook 自行取随机数。

Effect 权限取 `RoleSpec` 与 `ActionContract` 声明集合的交集。`EffectApplier` 拒绝未授权效果、越权目标、无效可见性或无法识别的效果版本。角色 Hook 即使存在缺陷，也不能获得直接状态写权限。

## 5. 调度点、顺序与响应窗口

核心只维护稳定的生命周期调度点，不维护角色名称：`GAME_SETUP`、`NIGHT_ACTION`、`NIGHT_COMMIT`、`DAWN_REACTION`、`DAY_ACTION`、`VOTE_ACTION`、`ROUND_END`、`GAME_END`。`ActionContract` 把行动绑定到调度点，并以整数 `order` 排序；同序时按 `role_id`、`contract_id`、行动者座位稳定排序，保证回放一致。

调度器在一个点内按以下顺序工作：生成资格快照、签发请求、收集/降级命令、逐契约聚合、由 Hook 生成 Effects、原子应用 Effects、派发新事件。只有当前顺序组全部提交后，后续顺序组才能看到其结果。因此女巫可以在狼人多数决已经产生当夜刀口后行动，而预言家查验不会影响刀口聚合。

响应窗口由契约声明的领域事件类型、原因过滤器、行动者资格和 `order` 打开，不在引擎中写角色分支。每个窗口具有稳定 `window_id = hash(game_id, source_event_id, contract_id, actor_seat)`。事件队列采用广度优先、稳定排序处理；同一窗口至多接受一次行动。系统设置单事件最大响应深度和单轮最大事件数，超过上限时停止后续响应、记录结构化故障并保持已提交事务一致，防止循环关系或错误 Hook 无限触发。

阶段推进前必须满足：当前调度点没有未完成请求、Effect 批次已提交、响应队列为空。游戏胜负检查作为通用阶段门禁运行，不由角色 Hook 自行跳转阶段。

## 6. 完整数据流

1. 服务启动时发现角色规范，注册表对 RoleSpec、Contract、Hook 签名、效果权限和可见性声明做静态校验。
2. 创建游戏时校验所有 `role_counts` 均已注册、数量合法、总数匹配，并验证角色组合约束；随后从规范初始化通用角色资源和私有数据。
3. Scheduler 到达调度点，按契约和资格声明枚举潜在行动者；通用投影器依据访问标签生成深度不可变的 `ActionContext`。
4. `is_applicable` 仅基于 Context 判断是否签发请求。请求绑定 actor、阶段、窗口、契约版本和幂等键。
5. 通用 PromptRenderer 使用 RoleSpec 的静态说明、ActionContract 和同一份 ActionContext 生成提示；它不再按角色名读取状态。
6. 模型优先通过 strict Function Calling 返回 `ActionCommand`；Parser 做严格结构校验，通用 Validator 检查请求归属、状态修订、次数、资源和目标基本合法性，角色 `validate` Hook 检查剩余客观语义。
7. `resolve` 或 `aggregate` Hook 从已验证输入产生 Effects。流水线自动在同一批次加入 `AcceptAction`，Hook 无法伪造其他行动键。
8. EffectApplier 对整批 Effects 做权限和前置条件校验，并以 compare-and-swap 方式原子提交；提交结果写入审计事件。
9. EventDispatcher 根据提交事件打开声明式响应窗口。响应行动重新走步骤 3 至 8，确定性 `react` Hook 也必须通过 EffectApplier。
10. 当前调度点和响应队列清空后，通用引擎执行胜负检查并推进下一调度点或阶段。

## 7. 错误、非法输出、降级与幂等

### 7.1 注册和运行时错误

- 重复 ID、未知调度点、非法 fallback、Hook 签名不匹配、未声明 Effect、无效可见性、资源 Schema 冲突和不满足的角色组合在启动或开局前直接拒绝，不能带病开局；
- `is_applicable` 或 Hook 抛出异常属于服务端规则故障，不伪装成玩家选择。当前 Hook 不产生 Effect，记录脱敏错误、角色版本和行动键；若契约有合法 `pass` fallback，则通过正常管线接受 fallback，否则暂停该局并返回明确的可恢复错误；
- Effect 批次校验或提交失败时不得部分写入。修订号冲突时重新投影一次并重跑纯 Hook；若行动键已提交则直接返回原提交结果，不重复结算；仍冲突则暂停该窗口并报警。

### 7.2 非法模型输出

strict 工具调用与 JSON 降级共用同一 Parser、Validator 和 Hook 语义校验。格式、Schema 或语义非法时，只允许在同一传输路径、同一行动键和同一 Context 修订上纠错重试一次；再次失败后提交契约指定的安全 fallback。网络或限流错误不被误判为 strict 不支持；只有供应商明确不支持 strict 时才切换 JSON 路径。fallback 不选择随机目标，夜间角色默认为 `pass`，投票默认为 `abstain`。

### 7.3 幂等

普通行动键至少包含 `game_id/round/phase/window_id/actor_seat/contract_id/contract_version`；响应行动还包含 `source_event_id`。解析重试、能力降级、连接重放和修订冲突复算都复用同一键。`AcceptAction` 与角色 Effects 同批原子提交，Effect ID 从行动键、序号和规范版本确定性派生。重复请求返回既有结果，不再次消耗药品、枪械或产生死亡；同一事件响应窗口也不能重复打开。

## 8. 内置角色兼容

### 8.1 狼人

狼人契约绑定 `NIGHT_ACTION` 的较早顺序，所有存活狼人分别提交 `kill` 或 `pass`，`aggregate` 按票数多数决并以稳定座位规则处理同票。目标只要求存在且存活，允许自刀和刀狼队友。狼人队友身份通过阵营关系的私有可见性标签进入 Context；不会进入好人 Context 或公开事件。

### 8.2 女巫

狼人聚合产生当夜待结算伤害后，女巫契约在后续顺序打开，每名存活女巫每晚只有一次 `witch_action`，枚举为 `save`、`poison`、`pass`。解药和毒药是两个单局一次的通用角色资源；`save` 只能指向 Context 中该女巫可见的当夜刀口，`poison` 只能指向存在且存活的玩家。有效行动在一个 Effect 批次中同时消耗对应药品并产生保护或毒杀，不能出现消耗成功而结算失败。Prompt 不生成阵营目标白名单。

### 8.3 预言家

预言家在 `NIGHT_ACTION` 提交 `check` 或 `pass`。有效查验产生只对该预言家可见的私有事实，公开状态和其他角色 Context 不包含结果。阵营判定由通用阵营标签投影为“狼人/好人”结果，不把目标的具体角色 ID 暴露给 Hook 或 Prompt。

### 8.4 猎人

玩家死亡提交后派发 `PLAYER_DIED` 事件。猎人契约声明监听该事件、行动者为事件目标、拥有未消耗的枪且死因不为毒；行动者可以已经死亡，因此不沿用普通“必须存活”资格。`shoot` 与枪资源消耗、目标伤害在同批提交，`pass` 不消耗枪。该响应窗口由事件声明打开，不在 GameEngine 中搜索字符串 `hunter`。

### 8.5 村民、未知角色与无行动角色

村民是合法的空 `contracts` RoleSpec；任何已注册的被动角色都可以没有行动，不会产生请求，也不会被自动赋予 fallback。配置中出现未知角色必须在开局前失败，不能降级成村民。已注册角色在某调度点无适用行动者时返回空请求集并正常推进；角色缺少本应存在的 Contract、Hook 或资源声明属于注册错误，而不是运行时静默跳过。

## 9. 注册与配置验证

注册表在服务启动时构建不可变快照，并验证：

- role/contract ID 和版本唯一且格式稳定；所有 action 唯一，fallback 属于 action 枚举并满足目标空值规则；
- 调度点已知，order 在允许范围内，聚合模式与 Hook 完整；稳定同序规则不会产生不确定性；
- Hook 参数和返回类型精确匹配，Hook 模块通过禁止状态依赖的静态检查；
- 初始资源、角色私有数据和 Effect payload 均通过严格 Schema；效果权限不超出角色与契约声明；
- 可见性命名空间已注册，阵营/关系访问不会落入公开范围；
- 响应事件和原因存在，响应深度/事件数上限有效；
- 角色数量约束、依赖、互斥和玩家总数可同时满足。

创建游戏时只接受注册表快照中存在的规范版本。运行中的游戏固定使用创建时的版本和配置摘要；部署新版本不会无声明地改变旧局规则。存档加载时若缺少对应规范或迁移器，必须拒绝恢复并给出版本错误。

## 10. 隐私、View 与 Prompt 边界

游戏状态字段和事件字段使用 `PUBLIC`、`ACTOR`、`CAMP`、`RELATION`、`SERVER_ONLY` 标签。通用 ContextProjector 根据请求中的 actor 和 RoleSpec 声明求交集，先裁剪再冻结；角色 Hook 和 PromptRenderer 只能获得裁剪结果。公开观战投影继续从 `PUBLIC` 数据单独生成，不能复用角色私有 Context。

RoleSpec 可以声明读取命名空间和静态文案，但不能声明“把某角色的全部对象交给 Hook”。狼人阵营关系允许狼互知；其他角色默认只有公开信息、自身身份、自身资源和自身历史私有事实。预言家结果、女巫刀口、药品、猎人枪和角色推理均按最小范围标记。

PromptRenderer 是无角色分支的纯渲染器：输入只有 RoleSpec 静态说明、ActionContract 和 ActionContext；历史对话作为明确标注的不可执行数据块；不展示服务端验证规则推导出的目标白名单，不因阵营暗示策略。StateFilter 被通用标签投影器替代或收缩为其兼容外壳，不再检查 `witch`、`hunter` 等角色字符串。

测试必须分别断言“应该可见”和“绝不可见”，并扫描 Prompt、Context、事件和错误日志；不得只用前端隐藏作为隐私证明。

## 11. 迁移顺序

1. 用特征测试锁定现有狼人自刀/刀队友、女巫单夜单药与单局药品、预言家私有查验、猎人毒死不能开枪、平票复投及非法输出 fallback 行为。
2. 新增冻结版核心类型、Effect 代数、EffectApplier 和原子/幂等测试；暂不切换现有引擎。
3. 将现有 ActionValidator 改成纯校验器，资源预留和接受记录改为 Effects；为旧 Resolver 增加只产 Effect 的适配层。
4. 引入通用 Scheduler、ContextProjector、PromptRenderer 和响应队列，在 feature flag 下对旧管线做无写入影子比对。
5. 按狼人、女巫、预言家、猎人、村民顺序迁移为 RoleSpec Hooks；每迁移一个角色就删除对应引擎/Validator/Resolver/Prompt/Filter 分支并跑完整回归。
6. 删除旧的状态直写路径和影子适配层，保存格式升级到带 registry/spec/effect schema 版本的存档。
7. 仅新增守卫样例规范：每晚 `guard/pass`、目标必须存活、不得连续两晚守同一座位；通过通用临时保护和角色私有数据 Effects 实现，用它证明核心五个模块无需修改。
8. 完成性能、隐私、确定性回放、故障回滚和 100% 覆盖率门禁后再默认启用新管线。

## 12. 测试与质量门禁

严格采用 Red → Green → Refactor。每个生产模块的测试持久化在其同目录 `test/test_<被测文件名>.py`，同时保留现有集成测试入口。测试至少覆盖：

- 五个不可变类型的深度冻结、严格反序列化、额外字段拒绝和版本行为；
- 注册表所有失败路径、未知/被动角色、组合限制和旧局规范版本固定；
- Scheduler 的资格、稳定顺序、聚合、响应窗口、循环上限和阶段门禁；
- Context/Prompt 的正向可见性与身份、阵营、资源、私有历史泄漏反例；
- 每个内置角色的 happy path、边界、非法目标、资源耗尽、重复提交和 fallback；
- Hook 异常、非法 Effect、批次冲突、修订重试、无部分写入和全链路幂等；
- strict 成功、不支持 strict 后 JSON 成功、一次纠错成功、再次失败安全放弃；
- 守卫样例只新增规范/注册配置即可运行，且无需更改核心五个模块；
- 固定事件流可重复回放得到相同状态摘要和公开事件；
- 现有角色、投票和平票复投行为保持不变。

交付前运行 `pytest --cov=app --cov-branch --cov-report=term-missing`，语句和分支覆盖率均必须为 100%，任何缺失路径均阻止合并；测试不得依赖真实模型、API Key、网络、系统时间或非固定随机数。另运行类型检查、格式检查、静态禁止依赖扫描和完整前后端回归。覆盖率豁免、只测新增代码或手工验证均不能替代该门禁。

## 13. 性能与可观测性

Context 投影按状态修订号、actor、可见性策略版本缓存不可变公开片段；私有片段只合并当前角色允许的命名空间。Scheduler 只遍历当前调度点的契约和候选座位，稳定排序复杂度为 `O(n log n)`；Hook 不复制完整 `GameState`。单个同步 Hook 设定 50 ms 软预算和 200 ms 硬上限，超限按规则故障处理。模型调用仍是主耗时，不因 Hook 管线增加额外模型请求。

结构化指标至少包含：按角色/契约版本的请求数、解析失败、语义失败、纠错、fallback、Hook 异常、Effect 拒绝、修订冲突、响应深度、Context 大小和 Hook 耗时。日志只记录 ID、分类和摘要，不记录私有 Context、完整 Prompt 或模型 reasoning。

## 14. 发布与回滚

新旧管线由 `ROLE_PIPELINE_V2` 控制。先在测试环境和只读影子模式中对同一固定输入比较命令接受结果、Effects、最终状态摘要和公开事件；影子管线不得写状态。之后按新建游戏比例灰度，运行中的游戏固定其创建时管线版本，不能中途切换。

每次提交保存管线版本、registry 摘要、spec/effect schema 版本和最近一致性检查点。出现异常时停止创建 V2 游戏并把新局切回旧管线；已经产生 V2 Effects 的游戏只允许由兼容 V2 的代码继续或从 V2 检查点恢复，不能把未知 Effect 强行交给旧代码。旧字段和读取适配器保留一个发布周期，确认所有活跃旧局结束且存档迁移可逆后再删除。

## 15. 验收标准

- `RoleSpec`、`ActionContract`、`ActionContext`、`ActionCommand`、`GameEffect` 深度不可变且有严格版本化 Schema；
- 任何角色 Hook 均无法获得或修改 `GameState`，EffectApplier 是唯一写入口，并保证批次原子性和幂等；
- Scheduler 只按调度点、顺序、契约和事件窗口编排，核心代码不存在内置角色名或动作名分支；
- 狼人允许自刀和刀队友；女巫每晚只行动一次且两种药各整局一次；预言家结果仅本人可见；猎人响应由死亡事件打开且毒死不能开枪；
- 未知角色在开局前拒绝，无行动角色合法且不会阻塞阶段；
- 非法模型输出最多纠错一次，此后确定性安全放弃；重复、重连和冲突重算不会二次消耗或二次结算；
- 新增守卫验收角色时，只新增角色规范模块及注册/配置，不修改 `game_engine.py`、`action_validator.py`、`action_resolver.py`、`prompt_builder.py`、`state_filter.py`；
- 新增人数或调整角色数量只修改配置，所有角色组合在开局前完成兼容性验证；
- 现有 Prompt 隐私、观战脱敏、投票和平票复投以及五个内置角色的既有合法行为保持；
- 全部单元、集成、隐私、确定性和回放测试通过，`app` 语句及分支覆盖率均为 100%，验证输出完整审阅后才能合并。
