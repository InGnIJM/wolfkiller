## 2. 架构决策

### 2.1 多目标命令（D1 缩小版，T1）

- `ActionCommand` 新增 `target_seats: tuple[StrictInt, ...] | None = None`；`target_seat` 与
  `schema_version` 一个字不改（旧命令字节形状不变，`Scheduler._fallback` 的
  `ActionCommand(action_type=..., target_seat=None, ...)` 继续可用）。
- `ActionContract` 新增 `multi_target_actions: Mapping[str, int]`（`_freeze_int_mapping` 冻结），
  声明「哪些动作恰好要几个目标」。
- 注册表静态校验：键 ⊆ `action_types`；每个计数 ≥ 2；与 `actions_requiring_target` 不相交；
  fallback 不得是多目标动作；**同一契约内所有多目标计数必须相同**（工具 schema 才能写死
  `minItems`/`maxItems`）。
- 校验器分支：多目标动作要求 `target_seats` 是**恰好 N 个互不相同**的正整数且全部 ∈ `alive_seats`，
  且 `target_seat is None`；非多目标动作要求 `target_seats is None`（违规码 `multi_target_forbidden`）。
- 解析器镜像同样规则（`target_count_invalid` / `duplicate_targets` / `target_seats_forbidden`），
  并扩 `coerce_payload_to_schema` 支持 `"array"`（`"[1,2,3]"` → `json.loads`；`"1,2,3"` → 按逗号/空白切分）。
- 工具 schema：`ActionContract.json_schema()` 条件化；`PromptRenderer.render` 里的手写 schema
  **改为直接 `contract.json_schema()`**（现有契约产出字节一致，用测试钉死），消除两份 schema 漂移。
- `TARGET_SELECTION_RULE` 追加一句多目标约束。
- `GameService._command_provider`：仅当 `request.contract.multi_target_actions` 为真时先
  `coerce_payload_to_schema` 再 `model_validate`，存量契约行为零变化。

### 2.2 `silenced` 通用通道（T2）

`core/night_settlement.py` 新增：

```python
SILENCED_STATUS = "silenced"
NIGHT_SCOPED_STATUSES = frozenset({SILENCED_STATUS})   # 每晚结算时清扫

def is_silenced(statuses: Mapping[int, object], seat: int) -> bool:
    return SILENCED_STATUS in frozenset(statuses.get(seat, ()))
```

三处门禁：

1. **调度器逐成员门禁**（`scheduler._run_point_locked` 的 `"normal"` 分支）：座位被封印 → 不调模型、
   不产出效果、不改状态，只往 `faults` 追加 `{"code": "actor_silenced", "seat": n, "contract": id}`。
   必须放在**执行期**而非 `issue` 期，否则同点内 order=10 的恐惧挡不住 order=50 的守卫。
   跳过只推进游标，journal/续跑不受影响（状态耐久，重放得到同一决定）。
2. **狼窝整队门禁**（`game_engine._execute_staged_night` stage 3/4）：`wolves` 中任一存活狼被封印 →
   跳过讨论、`director.record_votes(())`，并旁白 `("狼人阵营被封印", "今晚整个狼人阵营无法发动袭击。")`
   （不含角色名）。stage 5 照跑 → 全员 `pass` → 无伤害。**这一步必须做**：stage 4 的导演票经 provider
   直接喂给 `NIGHT_WOLF_VOTE`，只靠门禁 1 拦不住整队。
3. **清扫**：见 §2.3。

### 2.3 夜晚结算收口 `commit_night`（T15 + T2）

`EffectApplier` 新增薄封装（`settle_pending` 保持签名向后兼容，新增关键字参数默认 `False`）：

```python
def commit_night(self, state: GameState, *, round_number: int) -> CommitResult | None:
    """One atomic night-end batch: pool verdict + deaths + night-scope status sweep."""
    return self.settle_pending(state, round_number=round_number, night_end=True)
```

`settle_pending(..., night_end=False)` 内：

1. `night_end=True` 时先算舞池裁决 `settle_pool(...)`；`deaths = pool_deaths + settle_deaths`
   （按座位去重，**舞池死因优先**）。
2. 清 `in_pool` / `masked`（仅池内座位）与 `NIGHT_SCOPED_STATUSES`（全体座位）。
3. 早退条件扩展为「无 pending damage/protection **且**无舞池裁决 **且**无可清扫状态」→ 否则返回 `None`
   （存量「空结算返回 None」的测试仍绿）。
4. `scheduler._run_point_locked` 的 `NIGHT_COMMIT` 工作项改调 `applier.commit_night(...)`；
   响应窗口 follow-up 与白天路径一律保持 `settle_pending`（**不清扫**：白天中断结算若清扫，会把
   赤月使徒刚施加的封印立刻抹掉）。

封印只作用于**夜间行动窗口**；天亮后的死亡响应（猎人开枪等）不在封印范围内 —— 响应契约本来就有
各自的 `response_reasons` 白名单。

### 2.4 `role_checks` 读取通道 + `in_pool` 可见性（T3）

- `ContextProjector._actor_private_facts` 新增 `role_checks` 分支 →
  `role_private_facts_view(state, seat, "role_checks")`，逐条用新 `_project_role_check_result`
  （`target` 正整数 + `role` 合法 token ≤128，最多 20 条，坏记录丢弃）→
  `facts["role_checks"] = ({"target": n, "role": "..."}, ...)`。**石像鬼旧缺口随之修复。**
- `_PUBLIC_STATUSES` 加入 `"in_pool"`：只有声明
  `selected_target_fact_namespaces={"status_labels"}` 的契约（当前仅假面）能读到，且只到纯 hook、
  不进模型 prompt。

### 2.5 `hunt` 延迟死亡（T8）

- `HUNTED_STATUS = "hunted"`；`_DELAYING_CAUSES = _DELAY_CAUSES | {"hunt"}`（`_DELAY_CAUSES` 语义不变，
  `tests/test_values.py` 既有断言不动）；
- `delayed_death_statuses("hunt") == (HUNTED_STATUS, DELAYED_DEATH_STATUS)`；
  `_DELAYED_DEATH_CAUSES[HUNTED_STATUS] = "hunt"`；
- `settle()` 延迟分支条件改为
  `role_resources.get(target, {}).get(DELAYABLE_RESOURCE, 0) > 0 or cause in _DELAYING_CAUSES`；
  `held` 为空即当场死亡（老酒鬼被夜刀当夜死的语义保持）。

### 2.6 舞池结算 `settle_pool`（T15）

```python
DANCE_POOL_STATUS = "in_pool"
MASKED_STATUS = "masked"
DANCE_CAUSE = "dance"

def settle_pool(
    statuses: Mapping[int, object], camps: Mapping[int, str],
    alive: Mapping[int, bool], round_number: int,
) -> tuple[tuple[dict[str, object], ...], dict[int, tuple[str, ...]]]:
    """舞池少数方出局。被戴面具者在比较中折算成对立方阵营，camp 字段本身不动。"""
```

- `pooled` = 持有 `in_pool` 且 `alive[seat]` 的座位（升序）；`len != 3` → `((), cleared)`；
- `effective_camp`：`masked` 在身 → `good ↔ werewolf` 翻转，只影响本次比较；
- 同阵营 → 无人出局；不同阵营 → 人数少的一方出局；返回 `deaths`（`cause="dance"`）+
  `cleared`（每座 `(in_pool, masked)`），由 §2.3 的批次原子应用与清扫。

防护来源：`_WOLF_ONLY_SOURCES` 增加 `"dance_veil"`（自动进 `_PROTECTION_SOURCES`；
`_DOUBLE_SAVE_SOURCES` 不变 → 舞池盾不触发对穿）。

### 2.7 赤月使徒的「延迟出局」（T11，替代 C2）

```
CRIMSON_LINGER_CONTRACT: @ EXILE_VERDICT，action_types=("linger",)，
  actions_requiring_target=frozenset()，fallback_action_type="linger"，
  response_event_types={"EXILE_PENDING"}，response_reasons={"exile"}，

  trigger_reason == "exile" and actor_alive and resources["linger"] > 0 and
  <自己是最后一个狼阵营存活座位>     # camp_members(CAMP) + alive_seats(PUBLIC) 可算
```

  `is_applicable = actor_alive and round_number >= 2 and len(alive_seats - pooled_seats) >= 3`；
  `validate`：恰好 3 个互不相同、全在 `alive_seats`、均 ∉ `pooled_seats`；resolve：3×
  `ADD_STATUS(seat,"in_pool")` → `SET_PRIVATE_DATA(pooled_seats = 旧值 + 3 座)` →
  `EMIT_EVENT(DANCE_POOL{seat, pool_seats, round_number})` → 若 `actor_seat ∈ targets`：
  3×`SUBMIT_PROTECTION(seat, 1, "dance_veil")` → `EMIT_EVENT(DANCER_REASONING)`。
- **假面 mask_grant**：`order=30`（**在舞者之后**，"查验是否在舞池"才有意义）；
  `is_applicable = actor_alive and round_number >= 2`；
  `selected_target_fact_namespaces={"status_labels"}`；`validate` 拒连续两晚同一目标；resolve：
  `SET_PRIVATE_DATA(last_masked=target)` →
  `SET_PRIVATE_DATA(pool_checks = 旧值 + {"target": t, "in_pool": bool})` →
  `ADD_STATUS(target,"masked")` → `EMIT_EVENT(MASK_GRANTED{...})` → `EMIT_EVENT(MASK_REASONING)`。
  面具**只**参与舞池阵营折算，不改 `camp` 字段、不影响屠边判胜与预言家查验。

## 7. 迁移注记（旧档影响）

`ActionContract` 新增 `multi_target_actions` 字段会改变**所有**契约的 `stable_digest()`，
因此 `persistence/recovery_compat.assess()` 对在跑/暂停的旧局会判
`drift`（`contract_digest_drift`），需要 `POST /api/games/{id}/recover|resume?force=true`
（前端收到 409 `confirmation_required` 时弹二次确认）才能续跑。

这是本次改造**唯一**的旧档影响：`ActionCommand` 从不落盘，命令字段是纯增量；调度点、
`PointKey` 形状、检查点字段集与 `registry.digest` 的盖章方式都没有变化。
**不得**为了保住旧局的 `exact` 判定而回退多目标改造 —— 契约字段是阶段 3.5 与阶段 4
（寻香魅影绑 2 人、觉醒预言家验 2 人）的共同地基。
